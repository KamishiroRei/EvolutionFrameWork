# 精简编程

先找到使用者实际走的入口、已支持的数据和调用契约。用最小的完整改动满足目标。优先修负责产生错误的层，复用已有实现、类型与错误路径。

## 约束额外分支

禁止无依据的防御性编程。每个新增兜底、校验或兼容分支都要能指出它处理的受支持输入、明确契约或实际故障，以及应由哪一层处理。

- 输入解析、权限、数据写入等边界按项目契约校验。在内部沿已建立的类型和不变量工作，发现契约缺失时修负责它的边界。
- 支持范围内的旧数据按实际迁移约定处理。新增第二套路径前，先确认现有路径为什么无法承担要求。
- 失败需要可定位。按调用方的契约返回错误，使用现有恢复机制。结果未知时先核对状态，避免重复写入、发布或其他副作用。

例如，某按钮在合法配置下偶尔不显示。先查它的绑定、状态与真实渲染入口。若状态在加载时被覆盖，修复状态来源，并沿同一入口核对显示。另造默认按钮会让同一个功能有两个所有者，下一次变更还要同时维护两处。

## 验证改变的行为

选择能发现本次回归的现有检查，沿用户实际使用的入口验证。需要构建时走项目正式入口。已有依据可以复用。只有现有检查覆盖不到具体风险时才考虑补测试。交付说明实际观察到的结果和仍影响使用的限制。
