# 精简编程

先还原正常使用、实际故障及其因果关系，以功能、表现、性能和完成效率选择最小的完整改动。优先修负责产生错误的状态、数据、对象归属或时序，复用已有实现、类型与错误路径。

## 从原因修正实现

内部状态和后续处理由实现承担，使用者的正常操作保持顺畅。新增检查、拒绝、等待、兜底或兼容分支会改变使用条件，应能说明它如何实现实际功能要求或已查证的业务规则。用户目标之外的安全、稳妥诉求，以及既有代码或发生过故障本身，不构成新增限制的依据。

- 输入格式、数据范围和状态条件按实际功能需要处理，内部沿已建立的类型与对象归属工作。已有检查和契约同样核对其真实来源，AI 自选的实现限制不自动成为业务要求。
- 支持范围内的旧数据按实际迁移约定处理。新增第二套路径前，先确认现有路径为什么无法承担要求。
- 失败需要可定位。按调用方的契约返回错误，使用现有恢复机制。结果未知时先核对状态，避免重复写入、发布或其他副作用。

例如，后台结算重试使使用者无法继续下一步。应查清结算的数据归属和生命周期，让后续处理使用原任务的正确上下文。若业务本身允许继续操作，“所有结算成功”就是多加的前提，为它增加等待、缓存和重放会继续放大改动。修复应撤掉该前提及其衍生路径，同时核对正常操作和结算结果。

## 最低限度处理与直接交付

按用户目标完成实现，只做避免报错、支持正常运行所需的最低限度处理。需要编译时使用项目正式入口，完成必要构建后直接交付。

**严禁日常开发后检验，能不进行测试就不进行测试。** 禁止以安全性、一致性、完整性、可靠性或防御为目的，执行与当前功能开发无关的检查。不得追加哈希核收、二次回读、保存后重载、冷进程重开、影响面复查、回归、成套静态检查、夹具、采样或多规格对照，也不为这些目的编写测试。

即使修 Bug，也只沿现象、实际错误、已有日志和直接相关实现快速定位。已有信息足够就直接修复，不强制先复现、补证据或铺开调查。确需观察时只取得能决定改法的最少信息，修复后完成必要构建并交付，问题解决即结束，不追加修后测试、回归或验证闭环。报告实际完成事项，不以补齐证据层级为由新增操作。
